# Architecture Decision Record (ADR)

# ADR-002: Prisma ORM Selection

- **Estado:** Aprobado
- **Fecha:** 2026-07-12
- **Autor:** Antigravity (AI Architect)

---

# 1. Contexto (Context)
Campus Arena utiliza una base de datos relacional PostgreSQL estructurada por esquemas lógicos. El acceso a los datos debe ser tipado de extremo a extremo (Type Safe) para evitar errores comunes de sintaxis SQL en tiempo de ejecución y para simplificar las migraciones físicas de base de datos a medida que el modelo competitivo y de negocio evolucione.

---

# 2. Decisión (Decision)
Hemos elegido **Prisma ORM** como la herramienta de mapeo objeto-relacional para interactuar con la base de datos de PostgreSQL.

---

# 3. Justificación (Justification)

1. **End-to-End Type Safety:** Prisma autogenera tipos de TypeScript basados en el archivo `schema.prisma`. Al realizar consultas, el cliente de Prisma sabe exactamente qué columnas e interfaces se están retornando, reduciendo a cero los errores de tipos.
2. **Esquema Declarativo Intuitivo:** La sintaxis de Prisma es altamente legible y fácil de interpretar tanto por desarrolladores como por agentes de IA.
3. **Manejo de Migraciones Automatizado:** `Prisma Migrate` genera archivos SQL de migración limpios y predecibles, evitando scripts manuales de base de datos.
4. **Soporte para Múltiples Esquemas (MultiSchema):** Prisma soporta nativamente la separación por esquemas de PostgreSQL mediante la bandera de previsualización `multiSchema`, permitiendo aislar el dominio `auth`, `tournament`, `payments`, etc. sin tener que fragmentar la base de datos en múltiples instancias físicas.

---

# 4. Consecuencias (Consequences)

### Positivas
- Tipado estático asegurado en todas las consultas del repositorio NestJS.
- Documentación visual y declarativa directa de las relaciones relacionales de base de datos.
- Agilidad en el refactor de tablas y columnas mediante `prisma migrate`.

### Negativas
- Sobrecarga de rendimiento menor comparado con SQL nativo o query builders de bajo nivel como Knex en consultas extremadamente masivas (mitigable con caching de Redis).
- Limitación en queries no relacionales ultra-complejas que requieran queries recursivas avanzadas (en cuyo caso se permite el bypass controlado a raw SQL bajo las reglas del playbook).
